# 如何知道对方需要我做什么

共享规范仓库的 Issues 是唯一交接队列。工作仓库存 PR 和 Q&A；每次需要对方动作时，本仓库创建或更新一个交接 Issue，设置 label=handoff、Assignee=下一行动人。

## 一条交接需要写什么

```text
工作对象：https://github.com/owner/repo/pull/12
发起人：lw-liuwang
下一动作：review-pr
模式：normal
完成条件：核对第2节推导和手算，正确则合并，需要修改则列明问题并交回作者。
结果：提交、review、答案或合并的链接。
```

Issue assignee 表示现在轮到谁，不是永久负责人。标注 repo/URL，不能只写 #12。每个对象只保留一个活动交接 Issue；重跑先查已有分支、PR、讨论和交接，不重复创建。

每轮用 `Inbox` 查看指派给自己的任务，以及自己发起而等待对方的任务。优先收敛反馈和待验证内容，然后新任务。无待办时主动研究和撰写主题内容，不必空等。超过一天未回应，在每日摘要记录一次，不自动代替对方操作。

一轮以处理6–10条PR为目标，逐条完成核查、实际补写、合并或退回；同时处理Q&A，不把每一次review、采纳或合并各留到下一轮。单纯列出等待对方的PR不算完成处理，核查后有具体反馈的PR也不等于已合并。待办不足6条就先做已有的，再准备其他独立知识问题，不空等凑齐，也不拆同一个知识问题来补数量。6–10条是批次目标，不是必须合并的配额或每日硬上限。交接后继续其他主题；只有被交接的分支暂停原作者写入，不暂停账号的其他工作。收尾再查一次队列，已经收到的新结果可立即处理，无需等下一次唤醒。

## PR

主要贡献路径：A 向 B 的 RSI 仓库开 PR，由 B 验收合并；B 向 A 的 CS336 仓库开 PR，由 A 验收合并。Pull Shark 归 PR 作者。两边也可维护自己的仓库，但单独记录，不用仓库所有者身份推断未知计数。

普通流程：

1. 作者完成实际改动、开 PR，创建交接 Issue 指派对方，写 review-pr 和验收条件。
2. 对方检查当前 diff。需要修改，在 PR 说明具体问题，交接改派作者，动作 revise-pr。
3. 作者修改并回复，再把交接改派对方。通过后工作仓库负责人合并并记录结果，关闭交接 Issue。

需要对方实际补充时，动作改为 contribute-pr，说明补充什么；此时原作者暂停修改同一分支。接收方完成补写并核对整个最终 diff 后，可直接标 ready、合并和关闭交接；不默认再经过 verify-pr 和第二次合并交接。存在未解决的内容问题时才交回作者修改或确认。真正共同完成同一提交时保留 `Co-authored-by: Name <GitHub关联邮箱>`，只 review 不强加共同作者。默认 merge commit 保留共同署名提交。

具体配对方式：PR 作者先完成解释和初稿提交，开 draft PR，交接写明请对方补手算、反例或图。对方在同一分支补充真实内容，将双方成果整理到同一个共同署名提交，核对初稿和补充的推导、来源与最终 head，通过后当轮标 ready 并 merge。若初稿只有一个提交，可以在双方已交接分支写入权时 amend 该提交，保留原 author、添加另一人的 Co-authored-by，并用 `--force-with-lease` 指定原先核对的远端 head；不要改写主分支。也可以先交换补丁，由作者一次提交整合后的共同成果。普通完整贡献直接开 ready PR；Draft 只用于尚需补写的内容，不要求每条 PR 都做配对。

例如 B 向 CS336 开 PR：B 写解释，A 补一个带完整中间结果的手算，将双方内容整理到一个共同署名提交；A 作为接收方核对整个最终 diff，通过后同一轮 merge。反向在 RSI 做同样的协作。共同作者邮箱在接受邀请后通过对方关联的 commit 或本人确认取得，不凭空捏造身份。

合并前重新核对最终 head，使用 `gh pr merge <URL> --merge --match-head-commit <SHA>`；读取实际 merged 和落地 commit。引用共享任务使用 Refs，不让 Closes 提前结束交接。若对象已经成功而回填失败，补记录即可，不重做。

## Q&A

开启工作仓库 Discussions，选择 isAnswerable=true 的 Q&A 类别。

- A 在 CS336 提实际问题，交接指定 B：answer-qa。
- B 回答并记录答案链接，把交接改派 A：verify-answer。
- A 验证正确后采纳，读取 discussion.answer.id，关闭交接。
- 有问题则说明具体原因，改派 B：revise-answer。
- B 在 RSI 提问、A 回答时完全反向执行。

Galaxy Brain 归被采纳答案的回答者。PR 评论不替代 Q&A；不能把自己发起的讨论自答自采纳当作可靠路径。问题与回答围绕实际学习工作，验证通过再采纳。

## YOLO

这条流程与普通 review 分开。作者开一个实际文档 PR，请求已接受邀请的对方 review，交接 mode=yolo、Assignee=作者、动作 merge-yolo。另一方看到 reviewer 请求，先看交接，不提交 review。

作者检查 reviewers 请求存在、reviews 为空、当前 head 正确后自行 merge commit。记录结果并检查徽章；这是历史样本支持的下一次尝试，不保证当前条件完整。每账号先一次，未到账记录状态，不把未完成的尝试批量复制。

## 出错、暂停和修改规则

身份必须是本机自己的账号。读写对象以准确仓库和 URL 为准。API 写入超时先查询是否成功，不能盲目重发。review 后 head 改变就重新核对；没有对方权限时先邀请或交接给所有者。

用户说暂停时，停止后续写入并通过原生工具暂停本机任务，在共享 Issue 告知对方。恢复时继续现有对象，不重建。协议不设置全局控制 Issue、ready 屏障、每日硬上限或每次提交审批。规则、身份、权限、目标变更由人类决定。

每天每账号更新一条摘要，列出合并 PR、共同署名、采纳答案、可见成就和待对方动作。只有重要进展、故障或需要人类动作时通知。十四天总结银级进度；双方全部金级确认后各自暂停原生任务。
